# 01. Resolve each dependency from the VBlocks folder

**Date**: 2026-11-11

**Independent facts**:

- Node resolves a package name from the folder of the file that imports it, then
  from each parent folder
- npm nests or hoists each dependency a package declares, to reduce module
  duplication, in a way that Node still resolves the right version from the
  package's folder
- npm does not install an optional peer, one marked in `peerDependenciesMeta`.
  When another package installs it, npm does not place that copy within reach of
  the package that declares the peer
- Webpack resolves a loader named by a string from the folder the command runs
  in, not from its own folder

**Problem**:

- `webpack-cli` declares `webpack-dev-server` only as an optional peer
- In an npm workspace, npm can nest `webpack-dev-server` under VBlocks and hoist
  `webpack-cli` to the root. `vblocks serve` then fails: `webpack-cli` cannot
  resolve `webpack-dev-server`, and asks to install it
- The loaders of the default Webpack config, eg. `swc-loader`, can fail the same
  way

**Solution**:

- `vblocks serve` and `vblocks build` resolve `webpack-cli`, `webpack` and
  `webpack-dev-server` from the VBlocks folder, so they run the versions VBlocks
  declares
- The default Webpack config resolves its loaders, and the packages SWC adds to
  app files, eg. `@swc/helpers`, from the VBlocks folder too
- VBlocks declares `@swc/core`, to choose the compiler that matches its
  `@swc/helpers`

**Acknowledgments**:

- `swc-loader` loads `@swc/core` from its own folder, and the React Refresh
  plugin loads `react-refresh` from its own. Neither takes the package as an
  option, so each can load another copy than VBlocks'
- An ejected `webpack.config.js` resolves from the app folder, which declares
  VBlocks, not the loaders. They resolve only when npm hoists them there
